# Engineering Philosophy

This document collects the cross-cutting engineering philosophies that guide how everything in this ecosystem is built. Where the [standard layered architecture](architecture/STANDARD_LAYERED_ARCHITECTURE.md) describes *how a service is structured* — its [Api](architecture/API.md), [Embedded](architecture/EMBEDDED.md), [ServiceServer](architecture/SERVICE_SERVER.md), and the rest — this document describes *how we work*: the values that decide what counts as a real fix, an honest test, and finished work. Several of these principles have a fuller, more practical treatment elsewhere (especially in [Testing](architecture/TESTING.md) and [State Management](architecture/STATE_MANAGEMENT.md)); those documents are linked inline, and this page is the place where the principles behind them are named and explained. For the concrete, diff-level patterns that should raise a reviewer's eyebrows — reflection, timeout increases, resource increases, "the host is overloaded" claims, unmeasured performance claims, artificial test load and CPU spinners, missing test coverage, synchronous network IO — see the companion [Code Review Red Flags](CODE_REVIEW.md).

## Fix the Root Cause, Never Mask the Symptom

When code times out, fails intermittently, or runs slowly, that is a *symptom* — of a deadlock, a race condition, an unbounded loop or recursion, a resource leak, an inefficient algorithm, or a dependency that has gone unresponsive. The instinct to raise a timeout, lower a stress test's iteration count, drop in a `sleep`, or wrap the call in a retry loop is a reliable signal that the real cause has not yet been found, because none of those changes touch the underlying defect — they only make the failure take longer to surface while quietly eroding the very thresholds that exist to catch problems before users do. A timeout that "needs" to be increased is a bug that has not yet been understood. The only acceptable response is to investigate until the cause is known, fix that cause, and confirm the code now completes comfortably within the *original* limits. (See [Symptoms vs. Causes, Generally](architecture/TESTING.md#symptoms-vs-causes-generally) and the [OOM case study](architecture/TESTING.md#ooms-are-symptoms-of-memory-leaks-not-bugs-to-be-handled) for this principle applied to memory leaks.)

## Never Hide a Failure

A failing test is doing its job: it has caught something. The correct response is always to fix the code it caught — never to silence the signal. Deleting the test, marking it disabled, skipping it in CI, swallowing the exception in a `try`/`catch`, weakening an assertion (for instance from `assertEquals` to `assertNotNull`), or excluding it from the build all destroy information about a real defect while manufacturing the false comfort of a green build. A missing dependency or an incomplete environment is likewise a reason for a test to *fail loudly*, never a license to skip it with an assumption that silently passes without verifying anything — a skipped test reads as a pass but proves nothing. If a test genuinely encodes wrong behavior, that is a deliberate, explicit change to discuss and make on purpose, not something to paper over. (See [Never Skip Tests](architecture/TESTING.md#never-skip-tests).)

## Reproduce a Bug Before You Fix It

Every bug fix begins with a failing test that reproduces the bug — written *before* the fix and confirmed to fail *because* of the bug. This discipline forces a genuine understanding of why the bug exists and what the correct behavior should be before a single line of implementation changes; it proves the fix addresses the actual defect rather than something adjacent to it; and it leaves behind a permanent regression guard so the same bug cannot silently return. A fix without a reproducing test is a guess, and a guess that happens to work is indistinguishable from one that doesn't. This is **[test-driven development (TDD)](architecture/TESTING.md#test-driven-development)**, and it is the default way of working in this ecosystem for new features as much as for bugs — write the test that describes the behavior, watch it fail, then make it pass. (See [Test-Driven Development](architecture/TESTING.md#test-driven-development) and the [Bug Fix Testing Workflow](architecture/TESTING.md#bug-fix-testing-workflow); when a fix has already shipped and the production symptom is still there, start from the playbook [When a Fix Does Not Fix Production](playbooks/FIX_DID_NOT_HOLD.md).)

## Amplify Flakes with Real Concurrency, Never Artificial Load

A flaky test reproduces reliably when you exercise the exact narrow code path enough times, under enough genuine concurrency, to manufacture the interleaving the race needs — never by artificially slowing the machine down. Reaching for a CPU spinner, a busy-loop background thread, or any synthetic load introduced to "widen the timing window" is the wrong methodology, and it fails in two distinct ways. First, starving the CPU produces timeouts and scheduling stalls that may have nothing to do with the actual defect, so a test that fails under a spinner is failing for a reason you have not diagnosed, and a fix validated against it is validated against the wrong failure. Second, a spinner is an *unreliable* amplifier even on its own terms — it frequently fails to surface the underlying race at all, especially on hosts with more cores or different scheduling, where the extra load is simply absorbed and the timing window it was meant to open never opens. The correct amplifier is to drive the same narrow path at a high iteration count with real concurrency, which does double duty: it exercises genuine concurrent access to the shared state where the race actually lives, *and* it reaches that high iteration count far faster through parallelization. If reliable reproduction still eludes you, the answer is more iterations and more real concurrency against the true code path — not a heavier load on the box. Amplification is ultimately a discovery tool, though, and a reproducer must never be calibrated to a machine: once diagnosis names the exact condition the code mishandles, the reproducer graduates from statistical amplification to a deterministic trigger that forces that condition directly — one whose reliability varies with the machine it runs on is calibrated to a host, not to the contract, is not a reliable reproducer at all, and that variability is itself a sign the mechanism is not yet fully understood. (See [Prefer Parallel Iterations Over Serial `repeat`](architecture/TESTING.md#prefer-parallel-iterations-over-serial-repeat) and [Never Calibrate a Reproducer to a Machine](architecture/TESTING.md#never-calibrate-a-reproducer-to-a-machine).)

## Test End-to-End Against Real Dependencies

Tests verify a component's public API against *real* instances of its dependencies, not against mocks. When a test needs a server, it starts a real one; when it needs storage, it uses an in-memory implementation of the real interface. A mock only confirms that the code called the methods the test author expected — it cannot catch the protocol mismatches, integration bugs, and behavioral regressions that appear when the real parts are wired together, which are precisely the failures worth catching. Tests should also exercise only the public API, so that refactoring an implementation never breaks a test as long as observable behavior is preserved, and they should be [hermetically sealed](architecture/TESTING.md#tests-must-be-hermetically-sealed) and side-effect-free, preferring in-memory filesystems and databases to real ones so that the same test yields the same result on every machine, in any order, run alone or alongside the whole suite. (See [End-to-End Tests, Not Mocks](architecture/TESTING.md#end-to-end-tests-not-mocks) and [Test the Public API Only](architecture/TESTING.md#test-the-public-api-only).)

## Fix Bugs Upstream, Never Patch Around Them Downstream

When a leak, race, or correctness bug surfaces in a consuming service but originates in an upstream library, the fix belongs in the library — not in the consumer. A downstream workaround (a `try`/`catch` that swallows the symptom, a local fork or shaded copy, an added retry loop, a disabled feature) hides the bug from every other consumer of that library, hardens into permanent technical debt, and turns actively wrong the moment the library is updated. The correct path reproduces the symptom with a failing test in the consumer, isolates it with a failing test in the library, fixes the library at its source, publishes a new version, and bumps the dependency — closing the loop so the consumer's original test proves the upstream fix resolved the user-visible problem. Fixing upstream repairs the defect once for every consumer and keeps the dependency relationship honest.

## Performance and Reliability Are Features

Code is expected to be fast and reliable by default, and slowness or flakiness is treated as a defect to be diagnosed rather than a fact of life to be accommodated. Globally shared infrastructure — the build system, the P2P network — simply must work, so "it's just the environment" is a hypothesis to disprove with forensic analysis (heap dumps, thread dumps, connection state, protocol traces), not a conclusion to reach by default. The two most seductive forms of that excuse deserve naming, because both are almost always wrong: **"the JVM needs more memory"** (it doesn't — an `OutOfMemoryError` is a leak or a payload materialized in heap instead of streamed; take a heap dump and find what is actually retained, never raise `-Xmx`) and **"the host is over capacity"** (it isn't — the swarms are small and the work is light; an apparently overloaded box is the symptom of non-linear gossip, a thread or memory leak, or a JVM over-allocating heap until the OS swaps). When something is slow, the answer is to find and remove the cost — a connection leak, an allocation storm, a full re-serialization on every request, a stalled peer with an unbounded write backlog — never to wait it out with a longer timeout, an extra retry, an added delay, more heap, or a bigger machine. Performance and reliability are properties engineered into the system, not knobs to be relaxed when they become inconvenient. The same discipline extends to the tests that guard these properties: a test's verdict must never depend on which machine runs it, so bounds are generous by construction and complexity guards discriminate on an algorithm's shape, never a host's speed. (See [OOMs Are Symptoms of Memory Leaks](architecture/TESTING.md#ooms-are-symptoms-of-memory-leaks-not-bugs-to-be-handled), [The Host Is Almost Never Over Capacity](architecture/TESTING.md#the-host-is-almost-never-over-capacity), and [Test Verdicts Must Be Hardware-Independent](architecture/TESTING.md#test-verdicts-must-be-hardware-independent).)

## Measure Performance, Never Speculate About It

Performance problems are uniquely resistant to being reasoned about from the source. A bottleneck is rarely where a careful reading of the code predicts it will be — the hot path hides behind a lock nobody suspected, a payload materialized in heap instead of streamed, an allocation storm three call-frames deep, or a thread parked on synchronous IO while the profile shows the CPU idle — and the discipline that separates a real diagnosis from a plausible story is a single rule: **every claim about the cause of a performance problem must be backed by a concrete profile taken from the running production system.** A root-cause explanation supported only by looking at the code, however convincing it reads, is a hypothesis — and one that is wrong far more often than intuition admits — so be extremely skeptical of any performance claim that no measurement supports, most of all your own. Because so many performance issues turn out to be memory issues, two tools earn their keep before almost anything else: a **heap dump** to see what is actually retained, and a **thread dump** (`jstack`, sampled repeatedly into a poor-man's profiler) to see what the code is actually running or stuck on rather than what you imagine it is doing. Around them sits the rest of the kit — `vmstat` to establish whether the box is even CPU-, IO-, or swap-bound before blaming any one of them; `top` over an interval for per-process CPU; `jstat -gcutil` for GC pressure; and the heap dump again for whatever is driving memory. The culprits recur, so it pays to know the usual suspects the profile so often names: a blob loaded into memory instead of streamed, an unbounded in-memory cache that never evicts, an outright memory leak that retains what should have been released, runaway gossip amplification that multiplies messages non-linearly, unbounded thread launches where a bounded pool belongs, lock contention serializing work that should run in parallel, and any algorithm whose cost grows with the square of its input — each is common, and each is confirmed or ruled out by measurement, never assumed from a reading of the code. Only once the profile names the mechanism — *this* method, *this* allocation, *this* parked thread — is it time to fix it, and then the same measurement is what proves the fix moved the number it claimed to move. And the fix must be *systemic* — the removal of the mechanism the profile named — never a cap bolted in front of it: capping admission, throttling concurrency, or gating requests behind a semaphore to "keep the system below its saturation point" is a workaround that hides the defect and strips away the very signal needed to diagnose it, exactly like raising a timeout or growing a heap. That move is especially indefensible for a coordinator or manager service that delegates its real work to workers on separate hardware — such a manager should be so lightweight that its own CPU, memory, and thread footprint stays near-constant however many workers it drives, so if it saturates, that heaviness is *itself* the bug to profile and remove, never a load to be throttled with admission control (see [Prefer Cattle Over Pets](#prefer-cattle-over-pets-isolated-services-that-outlive-their-manager)). Beware especially the deploy that *appears* to fix a leak: restarting the process clears whatever had accumulated, so a freshly deployed build almost always looks healthy at first, and that early calm is not evidence the fix worked — a memory leak, a cache that never evicts, or a thread that is never reaped will simply climb again over the minutes or hours it takes to re-accumulate, and the restart alone would have produced the same momentary relief with no fix at all. Before declaring such an issue resolved, get a sense of its recurrence period first, then re-check the deployed fix after at least that long has passed, confirming the metric stays flat over time rather than merely starting low. This is [fixing the root cause rather than masking the symptom](#fix-the-root-cause-never-mask-the-symptom) and treating [performance and reliability as features](#performance-and-reliability-are-features), applied to speed; the companion [Code Review Red Flags](CODE_REVIEW.md#unmeasured-performance-claims) turns it into a reviewer's checklist, where an unmeasured performance claim — or a concurrency cap standing in for a real fix — is a flag to raise, not a conclusion to accept.

## A Refuted Hypothesis Is a Successful Outcome

An investigation exists to determine what is true, not to confirm what was suspected. When work is framed as "find the shared mechanism behind these failures," whoever does that work — a person or a delegated agent — is being quietly rewarded for finding the implied mechanism, and an investigator optimizing to complete the task will keep hunting for it long after the evidence has stopped supporting it. So give every investigation an explicit criterion under which the premise can be *positively refuted*, and treat an evidence-backed refutation as a first-class successful result: unless the stated expectation explicitly says otherwise, "the premise is wrong, and here is the evidence" is an acceptable — often the most valuable — outcome, because it redirects the plan before more work is spent on the wrong theory. The same license flows down through delegation: a delegate should be encouraged to contradict the premise it was handed when the evidence points elsewhere, and a delegate that declines an instruction with better evidence is the system working, not a failure to comply. (The playbook [Writing a Brief for a Delegate](playbooks/DELEGATION_BRIEFS.md) covers how to write that license, and the rest of a brief, down.) Pre-registered success criteria — decided before any results exist — keep this honest in both directions: they stop the investigator from renegotiating failure into success after the fact, and they stop the requester from dismissing an unwelcome refutation as noise. (See [Measure Performance, Never Speculate About It](#measure-performance-never-speculate-about-it) for the evidence discipline, and [Understand Before Fixing](architecture/TESTING.md#understand-before-fixing) for the same rule applied to flake hypotheses.)

## Avoid Special Cases, Optimize the General Case

When a path is slow, the tempting shortcut is to detect the *easy* case and route it around the general machinery — most commonly, sniffing whether a connection's peer is `localhost` or a loopback address and hand-tuning a fast path just for it while every other connection pays full price. This is the wrong instinct. A special case is code that must be written, tested, documented, and kept correct forever, and it forks every future change in two: the optimization reaches a privileged few, while the path most traffic actually travels — connections between distinct hosts across the mesh — stays slow. The right move is to make the *general* case fast, so that a loopback connection is quick simply because *every* connection is quick and the loopback peer is nothing more than the trivial instance of the same well-optimized path. Optimizing the general case is more maintainable (one path to reason about, not two), it hands the benefit to every caller rather than a lucky subset, and it removes the standing hazard that the fast path and the slow path silently drift out of agreement. A special case earns its place only when the general and special cases are genuinely, irreducibly different in behavior — never as a substitute for making the common path fast. This is the design-side complement of treating [performance and reliability as features](#performance-and-reliability-are-features), and it is exactly what the [direct-mesh-first connection model](architecture/STANDARD_LAYERED_ARCHITECTURE.md#connection-model-direct-mesh-first-relay-only-as-a-fallback) already embodies: every peer rides one uniformly-optimized connection instead of a lattice of purpose-built shortcuts, so the system is fast for everyone by construction.

## Migrate Heavily-Used Contracts Gracefully, Break Unused Ones Freely

The care a contract change deserves is proportional to how heavily the contract is used in production. A brand-new or lightly used service should just make the breaking change — spending migration machinery there buys nothing — while a service the fleet depends on (anything touching buildtest or NetLab affects the health of every build) must never break an existing function's contract, and a change to a function's *observable behavior* is a contract change even when the signature is untouched: truncating a result that was previously complete breaks callers just as surely as renaming the method, and recognizing that is the author's job, never something a reviewer or user should have to point out. The graceful path is deprecate-and-add: the server gains a new function with the better behavior, the old one keeps its exact contract until every deployed consumer can ride the new one, and the consumer-side client dependency implements both API shapes over whichever server function the connected server exposes — so consumers can adopt the new shape before the server ships it, deprecated callers keep working after the old function is deleted, and server and client rollouts proceed completely independently, with an end-to-end test matrix proving every configuration the field can contain. That fallback is routinely justified in only one place: the inherently decoupled server–client boundary, where version skew is a permanent fact of life. In embedded, in-process code there is no skew for a fallback to absorb, so a fallback there should almost never be used and should generally be rejected in review — it only hides defects in the new implementation, the migration-flavored version of [masking a symptom](#fix-the-root-cause-never-mask-the-symptom). The same never-break shape governs migrations of production *infrastructure*, where what changes is which system fills a role rather than what a function returns — pointing production CI at a new build/test backend, say. There the graceful path is a [parallel-run cutover](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#parallel-run-cutovers-for-production-infrastructure): run old and new side by side on real production traffic with only the old one required and the new one visible but informational, flip which one is required once they demonstrably agree, and delete the old one only after sustained confidence in the new one — so a proven system is authoritative at every moment, there is never a downtime window, and each phase reverts with a small configuration flip instead of a rollback under fire. (See [Graceful Migrations & Fallbacks](architecture/GRACEFUL_MIGRATION_FALLBACKS.md) for the full policy and patterns.)

## Errors Should Explain Themselves

An error message exists so that whoever reads it understands what went wrong and what to do about it. A good message states what was expected, what the actual value was, and why that value was wrong — `--test path must be a directory or a .kts file, but the provided path (/home/user/workspace/fav5) does not exist` rather than a bare `--test path must be a directory or a .kts file`. The reader should never have to open a debugger or read the source to recover information the program already had at the moment it failed. The same standard applies to anything user-facing: surface enough detail to fully understand and resolve the problem, and when asserting on errors in tests, assert against the *full* text so the quality of the message is itself protected.

## The Repository Is the Source of Truth

Work that exists only in a working directory, or only on a running server, is an operational risk: deployed code drifts from what is recorded, fixes live in places they can be lost, and no one can review or reason about what actually shipped. The risk starts long before the work is finished: local working trees are volatile, so in-flight work is checkpointed to a remote branch from the *first* meaningful milestone — a reliably-failing reproducer, a passing test, a completed sub-analysis — not gathered up in one push at the end. The running test is: *if this effort died right now, could a fresh one resume from the last checkpoint without redoing any finished work?* Completed work is committed to a branch, covered by comprehensive end-to-end tests, and opened as a pull request whose CI is driven all the way to green — and merged only with explicit human approval, never automatically. The repository, not a developer's machine and not a live container, is the authoritative record of what the system is; every other copy is derived from it and must be reconciled back to it. What the repository records is the system itself: the briefings, investigation notes, and scratch output that supported an effort do not become part of that record, and are not committed unless a user explicitly asks for them (see [Work-in-Progress Support Files](CODE_REVIEW.md#work-in-progress-support-files)). (This mirrors the broader [state management](architecture/STATE_MANAGEMENT.md) principle that derived state is never edited in place — only rebuilt from its authoritative source.)

## Prefer Cattle Over Pets: Isolated Services That Outlive Their Manager

Every service is an independent, disposable unit rather than a hand-tended pet — it can scale to zero, cold-start on demand, and be replaced wholesale instead of nursed back to health. A coordinator may manage many such services at once (distributing updates, checking health, orchestrating deploys), but its absence must never take a service down: with the manager gone, each service is still completely operational. That isolation is exactly what makes the system manageable at scale — one service's load can never starve another, dependencies are upgraded one service at a time instead of in a fragile big-bang, a failed or compromised service has a contained blast radius, a service can be relocated geographically without disturbing its neighbours, and a full backup is small enough to verify offline by restoring it on a laptop with the network unplugged and confirming exactly what was preserved. The costs are real and worth naming plainly: more independent things to run, more addresses to configure, and sweeping cross-service changes that are harder than a single central edit — trade-offs we accept because isolation buys a resilience a shared monolith cannot. The [ephemeral ServiceServer and WUI](architecture/STANDARD_LAYERED_ARCHITECTURE.md#serviceserver) already embody this: they hold no authoritative state of their own, so losing one loses nothing that was not already persisted in a dependency service.

## Decentralized by Default: Anyone Can Run It Themselves

A service should not require a central provider in order to exist. The same Api is available along a single [deployment spectrum](architecture/STANDARD_LAYERED_ARCHITECTURE.md#deployment-spectrum-embeddable-library-subservice-and-hosted-service) — as an in-process **Embeddable Library** with no IPC, as a **Subservice** the user self-hosts on their own hardware, or as a fully managed **Hosted Service** — and any consumer can be configured to reach each of its dependencies locally or remotely, so a parent can spin up a child service and keep full control over what that child is allowed to access (for instance hosting its own authentication module in-process rather than consulting a central authority). The model to aim for is Ubiquiti Unifi rather than Verkada: run it yourself, offline if you like, holding your own [W3Wallet](projects/W3Wallet.md) keys, and connect to a vendor's coordinator only for management and updates if and when you want them — never as a precondition for the service working at all. Bringing a service up requires only something on the port that can find and securely launch its code and act under the right identity, which [UrlResolver](projects/UrlResolver.md) bytecode fetch, the [SJVM sandbox](architecture/STANDARD_LAYERED_ARCHITECTURE.md#sandboxed-execution-and-security), and [ContainerNursery](projects/ContainerNursery.md) cold-start already provide. The honest limits: genuinely shared, deduplicated datasets are harder here — needing sharding for availability and decentralized access control for mutable data — and a few inherently privileged operations still require a remote authority; we treat these as known trade-offs of sovereignty, not reasons to recentralize by default. The fully decentralized, everyone-runs-their-own end of this spectrum is an aspirational direction tracked in [the plan](https://github.com/CodexCoder21Organization/PlanRepository/blob/main/BRAINSTORMS.md).
